# 04.5 — Separate Promotion persistence responsibilities

**What to build:** Keep Promotion lifecycle writes atomic behind `IPromotionRepository` while extracting repeated Domain Event and delivery persistence, and move User and Application Version queries to repositories owned by their respective modules.

**Blocked by:** 04 — Start an idempotent Deployment.

**Status:** ready-for-agent

**Branch:** `refactor/promotion-persistence`

**Architecture constraints:** Preserve one repository-owned PostgreSQL transaction for each Promotion snapshot, Domain Event, and initial delivery write; keep external Deployment calls outside that transaction; do not introduce a public Unit of Work, Domain Event repository, Domain Event bus, or delivery repository before another application-facing behavior requires one; keep one top-level type per matching file.

**Proposed commits:**

1. `refactor: extract Promotion event persistence`
2. `refactor: move User and Application Version persistence`

- [ ] Repeated `domain_events` and `event_deliveries` SQL is owned by one internal Promotion infrastructure writer.
- [ ] Event payload serialization and event-type-to-consumer subscription mapping are centralized in that writer.
- [ ] `PostgreSqlPromotionRepository` retains ownership of the connection, transaction, guarded snapshot transition, and commit.
- [ ] Promotion snapshot, exactly one Domain Event, and all initial delivery records remain atomic.
- [ ] Starting Deployment still invokes the external Deployment port before opening the persistence transaction.
- [ ] Requested events create an audit delivery, Approved events create audit and release-notes deliveries, and Deployment Started events create an audit delivery.
- [ ] Actor lookup moves from `IPromotionRepository` to a User-owned repository under the User module.
- [ ] Application Version lookup moves from `IPromotionRepository` to an Application Version-owned repository under the Application Version module.
- [ ] Promotion-owned progression and active-Promotion queries remain with the Promotion module.
- [ ] Consumer-shaped Promotion detail queries may continue joining Application Version data without exposing Domain objects.
- [ ] Command handlers depend on the owning repositories for Actor, Application Version, and Promotion access.
- [ ] Public HTTP behavior and the database schema remain unchanged.
- [ ] Focused integration tests verify the exact Domain Event and delivery rows and prove rollback preserves atomicity.
