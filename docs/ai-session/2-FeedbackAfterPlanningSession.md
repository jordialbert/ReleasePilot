I agree with the scope reductions and applied them to [PLAN.md](./PLAN.md:9), plus added [ADR 0007](./docs/adr/0007-split-domain-and-application-ports.md:1).

One architectural caveat: I would eventually move the four doubtful ports to Application too:

- `IDeploymentPort`: called by deployment orchestration.
- `INotificationPort`: called by a consumer.
- `IIssueTrackerPort`: called by the release-notes use case.
- `IDomainEventBus`: publishes events recorded by the aggregate; it is not used by the aggregate itself.

Operating on a `Promotion` does not automatically make an interface a Domain concept. The domain event types remain Domain concepts, while publishing them is Application orchestration. Keeping repository interfaces in Domain is still defensible because repositories are established DDD aggregate-persistence contracts.

For now, the requested split is preserved exactly in the ADR: only `IUnitOfWork` and `ILanguageModelPort` moved to Application.

The plan also now specifies:

- One worker process hosting all three consumers.
- One happy-path E2E journey.
- `GetWorkItems(promotionId)`.
- Swagger enabled at `/swagger` in every environment.
- Exact images: SDK `10.0.302-noble` and ASP.NET `10.0.10-noble`, verified against Microsoft’s official [SDK](https://github.com/dotnet/dotnet-docker/blob/main/README.sdk.md) and [ASP.NET runtime](https://github.com/dotnet/dotnet-docker/blob/main/README.aspnet.md) tag listings.
